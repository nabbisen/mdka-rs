# RFC 048 — The `3.0` surface: one result model, one convention per language, two modes

**Status.** Accepted — owner, 2026-09-25; §11 answered the same day, see §12
**Author.** Architect
**Created.** 2026-09-25
**Milestone.** `3.0` (breaking), **immediately after `2.9.0`** — owner, 2026-09-25. The `2.9.0` precondition slice is §7.
**Supersedes in scope.** RFC 039 Half B and RFC 041 §5.1, which the owner decided (2026-09-24) to settle together. Neither is restated here; both are *resolved* here.
**Source.** The pre-`3.0` audit, 2026-09-25 — the surface read from `src/lib.rs`, `node/index.d.ts` and `python/mdka/__init__.py`, and every behavioural claim below checked against the **published `2.8.0`** artifacts.
**Touches.** `src/lib.rs`, `src/options.rs`, `node/src/lib.rs`, `python/src/lib.rs`, `cli/src/main.rs`, `docs/src/`.

---

## 1. What `3.0` is for

> Today the same operation returns **three different result shapes**, one binding holds **two conventions at
> once**, and the configuration surface advertises **five modes and eight options** to deliver **two
> behaviours and two working options**.

`3.0` makes the surface equal the behaviour. **No conversion output changes** — not one byte, in any mode.
That is the constraint that makes this affordable: a consumer's Markdown is unaffected, and the migration is
a compile-and-rename exercise, not a re-verification of their corpus.

## 2. Three corrections to my own audit, made before designing on it

The audit is the input to this RFC, so its errors would become design errors.

**2.1 "Rust and Python did not follow the `_many` convention" — Rust cannot, and should not.** RFC 039 §1.1
already settles this: *"parity means the same operations exist and behave the same, expressed idiomatically
in each language — not identical signatures."* Rust has no optional parameters, so a `_with` pair **is** the
idiomatic form. Python's `_with` pair is a defensible choice too.

**The binding that is actually inconsistent is Node**, with itself: `htmlToMarkdownWith(html, options)` next
to `htmlToMarkdownMany(htmls, options?)`. Two conventions, one language. §4 fixes that.

**2.2 The string-form gap is narrower than RFC 041 §10 implies.** Checked against `2.8.0`:

| Surface | `mode = "strict"` today |
|---|---|
| CLI | accepted, **warns** |
| Node | accepted, **warns** |
| Python | **`TypeError` — a string is not accepted at all** |
| Rust `FromStr` / `parse_mode` | accepted, **silent** |

So the unwarned population is **Rust callers who parse a mode from a string**, not "string callers"
generally. Smaller, and it changes the remedy — §6.

**2.3 An unknown mode is already a hard error everywhere**, not a silent fallback:

```
CLI   mdka --mode bogus   -> exit 1, "error: unknown conversion mode: bogus. Valid: balanced|strict|…"
Node  {mode:'bogus'}      -> throws  "unknown conversion mode: bogus"
```

That matters: at `3.0` a removed name would fall into *that* message, which tells a user their config is
**wrong** rather than **obsolete**. §6 turns that into the fix rather than the problem.

## 3. The result model — the one real design decision

### 3.1 The distinction is fallible vs infallible, not single vs many

RFC 039 §2.1 said Python's names *"describe the wrong distinction"*. Following that through:

- **String conversion cannot fail.** It returns a string, or a list of strings. **No result type at all**,
  in any binding. This is already true and stays true.
- **File conversion can fail**, and *how* it should report depends on how many files:
  - **one file** — the caller asked about one thing; failing the call is right, through each language's own
    error channel;
  - **many files** — one failure must not abort the batch, so each file needs its own outcome, and the
    outcome must say which file it belongs to.

**Those are two different jobs, not an inconsistency.** The inconsistency is that today's types do not say
so.

### 3.2 Single-file conversion returns the output path, and fails through the error channel

`ConvertResult { src, dest }` carries `src` — which the caller just passed in. It is redundant, and in Node
it is worse than redundant: `ConvertResult` there declares `dest?` and `error?`, **fields the single-file
function never leaves unset or sets**. RFC 039 §2.1: *"a type that lies about its own invariants is the
least intuitive thing in this surface."*

**So `3.0` returns the destination path, and nothing else:**

| | `3.0` |
|---|---|
| Rust | `html_file_to_markdown(…) -> Result<PathBuf, MdkaError>` |
| Python | `html_file_to_markdown(…) -> str`, raises `MdkaError` |
| Node | `htmlFileToMarkdown(…) -> Promise<string>`, rejects |

**`ConvertResult` ceases to exist.** Not renamed — removed. Its single-file use had one useful field and its
bulk use is replaced by §3.3.

### 3.3 Bulk file conversion returns one named outcome type, in all three bindings

```rust
pub struct FileOutcome {
    pub src: PathBuf,
    pub result: Result<PathBuf, MdkaError>,
}
```

**Named for what it is** — the outcome for one file — so the name carries no claim about one-vs-many.
Rust expresses "exactly one of ok or error" in the type. The dynamic bindings flatten it, and **all three
gain the same predicate**:

| Field | Rust | Node | Python |
|---|---|---|---|
| `src` | `PathBuf` | `string` | `str` |
| `dest` | inside `result` | `string \| undefined` | `str \| None` |
| `error` | inside `result` | `string \| undefined` | `str \| None` |
| `ok` | `result.is_ok()` | **`boolean` — new; Node has no `ok` today** | `bool` |

**This resolves RFC 039 Half B §1 and §2 together:** one type across the bindings, a single answer to *"can
this fail"*, no `error` field on anything infallible, and Rust's `Vec<(&P, Result<…>)>` tuple is gone.

### 3.4 What this costs, per binding — Node pays most

| | Break |
|---|---|
| **Rust** | `ConvertResult` removed; single-file returns `PathBuf`; bulk returns `Vec<FileOutcome>` instead of a tuple vec. The tuple was anonymous, so nobody named it in a signature — **the cheapest of the three** |
| **Python** | `ConvertResult` removed (single now returns `str`); `BulkConvertResult` renamed `FileOutcome`, same four fields. **A rename plus one return-type change** |
| **Node** | `ConvertResult` removed. It served **both** single and bulk, so **every file-converting Node caller is touched** — and it is the binding whose type was lying, so it is also the one that gains most |

**Named plainly because it decides the migration guide's shape:** Node users get the longest section.

## 4. One convention per language, chosen for the language

RFC 039 §1.1's principle, applied consistently for the first time.

| | `3.0` |
|---|---|
| **Rust** | Keeps the `_with` pairs. No optional parameters exist; this is the idiom. **No change** |
| **Python** | Keeps the `_with` pairs. Consistent with itself since `2.4.0`. **No change** |
| **Node** | **Folds `With` away.** `htmlToMarkdown(html, options?)`, `htmlToMarkdownMany(htmls, options?)`, `htmlFileToMarkdown(path, outDir?, options?)`, `htmlFilesToMarkdown(paths, outDir, options?)`. The `…With` names are removed |

Node already argues for this in its own docstring, for `htmlToMarkdownMany`, citing RFC 039 §3 A2. `3.0`
applies the argument to the rest of the binding instead of to one function.

**Async.** Node keeps `htmlToMarkdownAsync(html, options?)` — one async form, options optional like the rest
— and its file functions stay `Promise`-returning. Rust and Python gain nothing async: neither has a runtime
to schedule on, and the work is CPU-bound. **This is now a decision rather than an accident**, and it is
recorded with its consequence: Node's async path cannot emit deprecation warnings, so anything `3.0`
deprecates later is invisible to Node file callers.

## 5. Modes and options: the surface becomes the behaviour

**Two modes: `Balanced` and `Minimal`.** `Strict`, `Semantic` and `Preserve` are removed — deprecated in
`2.8.0`, which is the runway this needs. **Keep both names as they are:** each is accurate, and renaming
costs every user a change that teaches them nothing.

**Options.** Eight fields today; **two affect output**.

| Field | `3.0` |
|---|---|
| `preserve_ids` | **Kept** — works |
| `drop_interactive_shell` | **Kept** — works |
| `preserve_classes`, `preserve_data_attrs`, `preserve_aria_attrs`, `preserve_unknown_attrs`, `drop_presentation_attrs` | **Removed.** Permanently inert — Markdown has no attribute syntax — and deprecated since `2.2.0` |
| `unwrap_unknown_wrappers` | **Removed, but it needs a `2.9.0` deprecation first** — §7 |

**`unwrap_unknown_wrappers` is the one genuinely awkward case.** It is inert *today* for a reason about the
renderer, not about Markdown, and `2.8.0` deliberately left it undeprecated on exactly that ground. So it
cannot be removed at `3.0` under this project's own rule: **nothing is removed that was never warned about.**

Two ways out, and I recommend the first:

1. **Deprecate it in `2.9.0` with an honest note** — not *"permanently inert"*, which would be false, but
   *"removed from the `3.0` surface; if wrapper handling becomes expressible it returns as a new option."*
   Removing it is then legitimate, and re-adding later is additive and non-breaking.
2. Keep it at `3.0` as a documented reserved field. **Rejected:** it leaves exactly the thing this RFC
   exists to remove — a switch that does nothing — inside the surface that is supposed to be honest.

**RFC 039 Half B §3 asked for "a documented path back".** Option 1 is that path, written into the
deprecation note rather than into a dead field.

## 6. `parse_mode("strict")` after removal — RFC 041 §10, answered

RFC 041 §10 offered accept-and-map or reject-with-a-message, and ruled out a bare `unknown conversion mode`
error because it *"tells a user their config is wrong rather than that it is obsolete."* §2.3 shows that bare
error is exactly what they would get by default, on the CLI and in Node.

**Recommendation: reject, with a message that distinguishes removed from never-existed.**

```
conversion mode 'strict' was removed in 3.0; it was an alias of 'balanced'. Use 'balanced'.
```

**Not accept-and-map**, because that keeps three dead names alive in string form indefinitely: a user's
config keeps working with a name that appears nowhere in the documentation, which is a worse kind of silence
than a break.

**The implementation is the elegant part.** `FromStr` is the single place every surface routes through — the
CLI, Node and `parse_mode` all call it. A removed-names table there gives **every** surface the right
message, including **the Rust caller nobody could warn** (§2.2). The one population the deprecation could not
reach is reached by the removal itself, at the moment it matters.

## 7. Sequencing — `2.9.0` is a precondition, not an option

| Release | Work |
|---|---|
| **`2.9.0`** | Deprecate `unwrap_unknown_wrappers` (§5). **Warn on the string form where a channel exists** — the CLI and Node already do; this adds nothing new but must be verified and asserted before removal. Nothing else |
| **`3.0`** | Everything in §3–§6, in one release, with one migration guide |

**`3.0` must not be split across two releases.** A user who migrates twice is a user who reads the guide
twice and forgives us once.

## 8. Acceptance criteria

1. **Zero conversion output change**, asserted over the `mode_identity` corpus against published `2.8.0`, in
   both surviving modes — the same comparison RFC 044's slice used, with a positive control.
2. `ConvertResult` gone; `FileOutcome` present in all three bindings with the four fields of §3.3, **`ok`
   included in Node**.
3. Single-file conversion returns the destination only, and fails through each language's own channel, with
   a test per binding that the failure is observable in the idiomatic way.
4. Node exports no `…With` name; every options-taking Node function takes them optionally.
5. Two modes; the five attribute options and `unwrap_unknown_wrappers` gone; `preserve_ids` and
   `drop_interactive_shell` remain.
6. **`FromStr` distinguishes the three removed names from unknown ones**, with §6's message, and the
   distinction is asserted on all three string surfaces — CLI, Node, and `parse_mode` directly.
7. **One migration guide**, covering both halves, with a per-binding section; **Node's is the longest** and
   says so.
8. The API reference is **tri-lingual before the guide is written** — see §9.
9. Existing counts pass, each with its command; all workflows green.
10. **The migration guide lists `unwrap_unknown_wrappers`' removal explicitly**, written on the assumption
    that the reader never saw its deprecation warning — see §12.1.

## 9. A documentation precondition, from the audit

`docs/src/api/index.md` claims to show *"the complete surface"*, has a **Language** column, and lists only
Rust — omitting three Rust functions and all nineteen Node and Python ones. `api/errors.md` is Rust-only in
58 lines.

**The migration guide cannot be the first document that shows the three surfaces side by side.** Fixing the
API reference is a `2.9.0`-or-earlier job, non-breaking, and it is where a user will look to understand what
`3.0` did to them.

## 10. Not in scope

- **Any conversion behaviour.** §8.1 is the hard constraint.
- Renaming `Balanced`, `Minimal`, or any surviving function.
- Async for Rust or Python (§4).
- Implementing wrapper preservation (§5) or any new option.
- The three stale `node/<platform>/` directories, the preflight script, `npm-install-gate`'s coverage — all
  tracked separately in `ROADMAP.md`.

## 11. Open questions for the owner

1. **`unwrap_unknown_wrappers`** — §5 option 1 (deprecate in `2.9.0`, remove at `3.0`) or option 2 (keep it
   as a reserved field)? My recommendation is option 1.
2. **`3.0` timing.** This RFC scopes the work; it does not schedule it. `2.9.0` must come first either way.
3. **bekoedit.** Correspondence is paused until the stable release. `3.0` changes no output, so their
   `Minimal` conversion is unaffected — but their **pin and their call sites** are not. Should they be told
   at `2.9.0`, so the deprecation reaches them before the removal does?

## 12. §11 answered — owner decision, 2026-09-25

| Question | Decision |
|---|---|
| **§11.1 `unwrap_unknown_wrappers`** | **§5 option 1.** Deprecate in `2.9.0` with the honest note, remove at `3.0`. The path back lives in the note, not in a dead field |
| **§11.2 `3.0` timing** | **Immediately after the `2.9.0` release.** `2.9.0` remains a precondition and is not skipped |
| **§11.3 bekoedit** | **Not at `2.9.0`.** Correspondence stays deferred to the stable release — `3.0.0` |

### 12.1 One consequence of §11.2, recorded rather than argued

**`unwrap_unknown_wrappers` gets a short runway.** Deprecated in `2.9.0` and removed in the release straight
after, few users will adopt `2.9.0` in between, so the warning will mostly be a *record* rather than a lived
warning.

That is acceptable here and the reasons are specific, not general: the option **is inert**, so its removal
breaks compilation and changes no behaviour; and the alias modes — the part of `3.0` that removes something
users actually name — had a full runway in `2.8.0`, which is what the rule exists for.

**The mitigation costs nothing and is now a criterion (§8.10):** the `3.0` migration guide must list
`unwrap_unknown_wrappers` explicitly, on the assumption that **nobody saw the warning.** A short runway is
survivable; a short runway plus a silent removal is not.

### 12.2 What §11.3 means in practice

bekoedit hears nothing at `2.9.0` and everything at `3.0.0`. Two things follow:

- **The `3.0.0` letter must carry `2.6.0` through `3.0.0`** — the `<sup>`/`<sub>` fix, the emphasis fix, the
  deprecations and the removals — not just the release it is sent for. The material is accumulating in the
  suspended `2.6.0` draft and in each release record.
- **They pin `= 2.5.1` and use `Minimal`**, so no output change reaches them at all. What reaches them is
  the **call sites**: `ConvertResult`, the Rust bulk tuple, and any mode name they pass. The letter should
  lead with that, not with conversion.
