## What the diagnostic actually showed

Nested `*mdka*` artifacts **were** in the restored cache — `deps/libmdka-*.rlib`, `*.rmeta`, `*.d`,
`libmdka_node.so`, fourteen or so in all. The report records them as "correctly absent" and annotates
one pasted line showing a present file as *"(correctly excluded — absent…)"*.

And they post-date the exclusion: `!target/debug/**/*mdka*` and `-v2-` landed together in `e9ef8c4`,
whose run began **2026-09-25 23:16 UTC**; the artifacts are dated **23:16:52** and **00:02:26**.
**A cache saved with the nested exclusion active still contains nested matches.**

So the pattern is not failing only at zero depth. **It is not excluding anything.** A second `!` line
would be the third inert cache patch in this project's history.

## What to do instead

1. **Replace both `!` patterns with an explicit step**, right after the cache-restore step, that
   deletes the workspace crates' compiled artifacts and **prints what it deleted**:

   ```yaml
   - name: Drop restored workspace artifacts (see notes below)
     run: |
       find target/debug -maxdepth 2 -name '*mdka*' -print -delete 2>/dev/null || true
   ```

   Adjust the shape to what the listing showed; the point is that a `find … -print` leaves proof in
   every run's log, whereas a `path:` exclusion leaves none. **This project has now guessed
   `actions/cache`'s glob semantics wrong twice. Stop guessing them.**

2. **Keep the `-v3-` key bump.** Still necessary, for the reason already in the file.

3. **Delete the "Verified against the change this is meant to catch" paragraph** from the comment. It
   describes a run that has not happened; your own report says so. Re-add it, worded to what
   actually occurred, once it has.

4. **Then run the unchanged-version proof** exactly as you planned it — it is now the only thing that
   separates a working fix from a cold-miss green. Your three-step plan is right; keep it.

5. **Revert `bba3f71`** before the release.
