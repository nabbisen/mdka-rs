## 1. A run of breaks must use the backslash when the option is on 🛑

Your fallback was reasoned from *"no break in the run has content before it on its own line."*
Measured, that is not how it parses — **a line of only two spaces is a blank line**, so the spaces
form splits the paragraph:

| input | spaces | backslash |
|---|---|---|
| `a<br><br>b` | **`para("a") para("b")`** | `para("a" HB HB "b")` |
| `a<br><br><br>b` | **`para("a") para("b")`** | `para("a" HB HB HB "b")` |
| blockquote run | **`quote(para("one") para("two"))`** | `quote(para("one" HB HB "two"))` |
| list-item run | — | `ul(li("one" HB HB "two"))` |

So in a run the default does not merely risk losing the break — **it loses the paragraph**, and the
backslash is the only form that keeps it. The option's own rule is *emit the backslash where the
break survives as a break*; in a run, only the backslash does.

- [ ] With the option **on**, every break in a run emits `\` + newline, in paragraph, blockquote and
      list item.
- [ ] Assert the **parse**, not only the bytes: a run of *n* breaks is one paragraph with *n* `HB`s.
- [ ] 🛑 **Do not change the default.** `a<br><br>b` → two paragraphs with the option off is a
      pre-existing defect that predates this RFC; fixing it changes everyone's output and needs its
      own RFC. Leave it, and note in your report that you left it.
- [ ] Correct the docs' reason along with the behaviour.

## 2. One documentation clause

> At the end of its block … **the spaces are dropped as trailing whitespace**

mdka does not drop them: off → `one··⏎⏎two`, on → `one⏎⏎two`. The *parser* ignores them. Say that
the default still writes them and they are inert there, while the option writes nothing.
