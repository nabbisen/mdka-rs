# Developer Handoff — RFC 045 · Python type stubs, and a checker that keeps them true

**RFC.** `rfcs/accepted/045-python-type-stubs.md` — accepted by the owner, 2026-09-25
**Milestone.** Unassigned; packaging and typing only. Release vehicle is the owner's call
**Priority.** P2 by impact, but see §7 — the false all-clear is live in every published wheel
**Prepared.** 2026-09-25
**Baseline.** `2ce39ac` — 605 Rust, 42 Node, 25 loader, 90 Python; seven workflows green
**Scope.** Stubs, a CI check, and a documentation paragraph. **No conversion change, no signature change, no other binding.**

---

## 1. What is wrong

The published wheel ships `mdka/py.typed` (0 bytes) and **no `.pyi` files**. The marker says "this package is
typed"; nothing then describes a type, so everything resolves to `Any`:

```
$ mypy --strict typecheck.py     # str->int, int-as-str, missing required arg
Success: no issues found in 1 source file
```

**Without the marker mypy says *"missing library stubs or py.typed marker"*, which is true.** We replaced a
correct warning with a false clearance — worse than shipping nothing.

## 2. The surface, read from the runtime

**Write the stubs from the built module, not from the documentation.** PyO3 emits text signatures, so
`inspect.signature` gives you the real shape. Two places where the documented and actual surfaces differ, and
both will fail `stubtest` if you take the docs at their word:

- **Three deprecated keywords are still accepted** — `preserve_classes`, `preserve_data_attrs`,
  `preserve_aria_attrs`. They are inert and warn, but they are part of the signature and must appear.
- **`preserve_unknown_attrs` is rejected** at runtime with `TypeError`. It must **not** appear.

The `_with` functions all take the same tail:

```
html_to_markdown_with(html, mode=..., preserve_ids=None, preserve_classes=None,
                      preserve_data_attrs=None, preserve_aria_attrs=None,
                      drop_interactive_shell=None, unwrap_unknown_wrappers=None)
```

Thirteen documented names: nine functions, `ConversionMode` (five members), `ConvertResult` (`src`, `dest`),
`BulkConvertResult` (`src`, `dest`, `error`, `ok`), `MdkaError(Exception)`.

## 3. `mdka_python` — smaller than the RFC implies

**Correction to RFC 045 §5, which I have also made in the RFC.** `python/mdka/__init__.py` already declares
`__all__` with exactly the thirteen names, so `mdka_python` is **not exported** — it is bound only as a side
effect of `from .mdka_python import …`. `from mdka import *` is already correct; only `dir(mdka)` and
attribute access show it.

**Mirror the existing `__all__` in the stub.** Note that `stubtest` checks a module and will follow to
`mdka.mdka_python` if it is importable, so decide deliberately whether that submodule gets its own stub or is
excluded from the check, and say which in the report.

## 4. `stubtest` is the point of this slice 🛑

A stub is a second description of the same surface. **Without a checker it is something that drifts**, which
is the failure this project keeps finding — `2.4.2`'s inert options, RFC 042's artifact contract, the mode
wording. `stubtest` compares the stub against the **live** module and reports anything missing, extra or
differently shaped.

- Run it in **CI**, not only locally. It imports the compiled extension, so the job must build it first —
  the Python job already does that for pytest.
- **Show it catching a deliberate mistake**: remove a keyword from a stub, watch `stubtest` fail, restore it.
  Paste both. A checker that has only ever passed has not been shown to work.

## 5. Criteria

1. The three lines of §1 **each fail** under `mypy --strict` with the right message. Paste the before
   (`Success: no issues found`) and the after.
2. `stubtest` passes against the built extension and **runs in CI**.
3. `stubtest` **demonstrated failing** on a deliberate stub error, with output.
4. All thirteen names present with their real shapes, including the three deprecated keywords, excluding
   `preserve_unknown_attrs`.
5. **The built wheel contains the `.pyi` files** — build it, list the archive, paste the listing. Do not
   trust the manifest; the `py.typed` marker got into the wheel and the types did not, which is how we got
   here. `py.typed` stays.
6. `docs/src/getting-started/usage-python.md` no longer says stubs are missing. Its hand-written signature
   list becomes redundant — remove it or point it at the stubs, and **do not leave two descriptions of the
   same surface**, which is the defect this slice exists to stop.
7. 90 Python tests still pass; 605 Rust, 42 Node, 25 loader untouched; seven workflows green.

## 6. Not in this slice

- Any conversion behaviour, option or binding signature.
- Node.js typings — `index.d.ts` is generated by napi and already checked.
- Removing `py.typed`. That was the fallback if stubs were not worth doing; the owner chose stubs.

## 7. Sequencing, and a question that comes back if this waits

Unlike RFC 040, 042 and 043, **there is nothing to hold**: the documentation change describes typing that
ships in the same wheel as the stubs, and the docs site saying "stubs exist" is false only for as long as the
release takes — the same window as any release.

But the false all-clear **is live now**, in every published wheel. If this slice is going to sit, the owner
asked whether to remove the marker meanwhile and I said the better answer was not to have an interim. **If
you cannot take this soon, say so** and I will put that question back to the owner rather than let a type
checker keep certifying broken code.
