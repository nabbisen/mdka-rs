# Developer Handoff — RFC 040 · npm platform coverage and an honest load error

**RFC.** `rfcs/accepted/040-npm-platform-coverage.md` — accepted by the owner, 2026-09-24
**Milestone.** M4 → a minor or a patch, owner's call at prep time; **after `2.4.2`**, which ships first
**Priority.** P2 for Part A, **P1 for Part B**
**Prepared.** 2026-09-24
**Baseline.** `89c3d1d` — 570 Rust, 42 Node, 90 Python; seven workflows green
**Order.** **Part B first.** If only one part lands, it must be B.

---

## 0. The two halves, and why B outranks A

**A.** npm publishes three platform families. The *same tag run* builds five for the CLI and six wheels for
PyPI, from recipes already in this repository. Only `release-npm.yaml` was left behind.

**B.** On any platform outside those three, `npm install` exits 0 in silence and `require('mdka')` then
reports *"npm has a bug related to optional dependencies … try `npm i` again after removing
package-lock.json and node_modules"*. There is no npm bug, the loop cannot terminate, and it contradicts our
own installation page, which describes the situation accurately.

Widening the matrix never reaches everyone — someone is always outside it. **The honest message is required
whatever is built**, and it is the cheap half.

## 1. Part B — own the error message 🛑

`node/index.js` is regenerated by `napi build`. **Do not hand-edit it**; a patch there is reverted by the
next build with nothing to warn you.

Add a committed wrapper and make it the entry point:

- **`node/loader.js`** — `require('./index.js')` inside `try`/`catch`.
  - On success, re-export unchanged, **including every named export**.
  - On failure, throw an error that names `process.platform`, `process.arch` and the libc where detectable,
    lists the platforms actually published, and links
    `https://nabbisen.github.io/mdka-rs/getting-started/installation.html`. Attach the original error as
    `cause`, so a genuine npm resolution bug stays diagnosable.
  - It must **not** mention the npm bug or advise reinstalling.
- **`node/package.json`** — `main` → `loader.js`; add `loader.js` to `files`. Check `types` still resolves.

**The export list must not be maintained by hand.** Re-export programmatically, or assert equality against
`index.js` in a test, so a future generated export cannot be silently dropped. Criterion 5 below is that
assertion.

Reproduce the current behaviour before you change it, so you can show the difference:

```
npm i mdka@2.4.1 --os=linux --cpu=x64 --libc=musl   # "added 1 package", no @mdka/* installed
node -e "require('mdka')"                            # the misleading error
```

**Rejected, do not do it:** adding `os`/`cpu` to the main package. It cannot express libc, and it breaks
installing on one platform to deploy to another.

## 2. Part A — three more targets

Add to `release-npm.yaml`'s matrix and `node/package.json`'s `napi.targets`:

| Target | Package | Copy the recipe from |
|---|---|---|
| `x86_64-unknown-linux-musl` | `@mdka/lib-linux-x64-musl` | `release-executable.yaml`, `release-pypi.yaml` |
| `aarch64-unknown-linux-gnu` | `@mdka/lib-linux-arm64-gnu` | `release-pypi.yaml` (manylinux aarch64) |
| `aarch64-unknown-linux-musl` | `@mdka/lib-linux-arm64-musl` | `release-executable.yaml`, `release-pypi.yaml` |

Three → six. These are **release-triggered** jobs (`on: release: [created]`), added in parallel. Nothing is
added to the seven workflows that run on every push — do not "optimise" this by moving work onto push.

Confirm `napi pre-publish` picks the new targets up into `optionalDependencies` automatically; if it needs a
list anywhere else, find it rather than assuming symmetry.

## 3. Documentation

`docs/src/getting-started/installation.md` and `README.md` must list six npm platforms, and the sentence
naming musl and Linux arm64 as unsupported must go. **This page is currently correct and unusually good —
the audit verified every claim on it. Keep it correct.** macOS Intel and Windows ARM remain unsupported and
must still be named as such.

## 4. Explicitly not in this slice

- **macOS Intel and Windows ARM.** Absent from all three channels; one project-wide decision, not an npm one.
- **The `wasm32-wasi` universal fallback** (RFC 040 §4 Part C) — needs the parallel feature and the
  performance cost measured first.
- Anything touching conversion output.

## 5. Criteria

1. The three new `@mdka/lib-*` packages are **published and resolvable on the registry** at the release
   version, and appear in `mdka`'s `optionalDependencies` — verified by querying the registry, not by a green
   workflow.
2. On **Alpine x64** and **Linux arm64**, in a container: `npm install mdka` then
   `require('mdka').htmlToMarkdown('<p>hi</p>')` returns `hi`. **Install-then-require**, not install alone —
   an install that exits 0 is the entire subject of this RFC.
3. On a platform still unsupported, the thrown message names that platform, lists the published ones, links
   the installation page, and **does not mention the npm bug** — asserted by matching the message text.
4. The original load error survives as `cause`, asserted.
5. Every export of `index.js` is exported by `loader.js` — asserted by comparing the two lists, not by eye.
6. `node/test.js` passes unchanged through the wrapper; 42 Node tests still green, plus the new ones.
7. All seven workflows green.

## 7. Committing and pushing — the rule, set by the owner 2026-09-24

**You may commit and push only work that is yours and has been approved.** Both halves matter:

- **Yours.** Only the files this handoff asks you to change. The working tree may hold commits and
  documents that are not yours — RFCs, handoffs, review records, release notes. Do not include them, do not
  amend them, and do not push a branch that carries them.
- **Approved.** Report back first (§6). Approval comes through that review. Do not push on the strength of
  a green test run: green is necessary and is not approval.

Also not yours: **tagging, releasing, or triggering any release workflow.** A release is cut against a
checklist by the architect, on the owner's authorisation.

If you are unsure whether something falls inside this slice, say so in the report rather than deciding it.
Ask before, not after — a push is visible and runs seven workflows.
