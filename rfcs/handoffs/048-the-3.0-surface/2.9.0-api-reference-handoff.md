## 1. Why this is P1 and not documentation tidying

**The migration guide must not be the first document that ever showed the three surfaces side by side.**
A user reading `3.0`'s guide needs a *before* to compare against, and today there isn't one.

From the pre-`3.0` audit, measured:

- `docs/src/api/index.md` opens *"The table below shows the complete surface — every function and type you
  need, nothing you don't."* Its Functions table has a **Language** column. **Every row says Rust.**
- It omits, for Rust: `html_to_markdown_many`, `html_to_markdown_many_with`, `version()`.
- It omits **all 10 Node functions and all 9 Python functions**.
- Its Types table omits `BulkConvertResult` (Python) and `JsConversionOptions` (Node).
- `docs/src/api/core.md` has sections for the same six and no others, so `_many`, `_many_with` and
  `version()` have **no API-reference page at all** — they appear only in usage pages.
- `docs/src/api/errors.md` is 58 lines with **zero mentions of Node or Python**.

## 2. Three statements that are wrong, not merely incomplete 🛑

Fix these first; they are the ones a reader can be misled by.

1. **`index.md`: *"`ConvertResult` — Returned by single-file functions: `src` + `dest` paths."*** True for
   Rust and Python. **False for Node**, where `ConvertResult` is returned by the **bulk** functions too and
   carries `error?`.
2. **`index.md` Guarantees: *"File functions propagate IO errors via `Result<_, MdkaError>`."*** Rust does.
   **Python raises**; **Node returns `error` in the struct**. Stated unqualified, it is a Rust fact
   presented as an mdka fact. The other three guarantees do hold everywhere — the trailing-newline one is
   verified, including the empty-input case.
3. **`index.md`: *"the complete surface"*.** Either make it complete or stop claiming it. **Make it
   complete.**

## 3. What to build

**Source the content from the code, not from the existing prose.** The three surfaces are
`src/lib.rs`, `node/index.d.ts` (generated) and `python/mdka/mdka_python.pyi`.

1. **`index.md`'s Functions table becomes tri-lingual** — one row per *operation*, with a column per
   language giving that language's name, and an em dash where a language does not have it. That shape makes
   the asymmetries visible instead of hiding them, which is the point:
   - Node has **no** `htmlToMarkdownManyWith`;
   - Node has `htmlToMarkdownAsync` / `htmlToMarkdownWithAsync`, which **neither other binding has**;
   - Node's file functions are **async-only**.
2. **The Types table gains `BulkConvertResult` and `JsConversionOptions`**, and says for each which language
   it belongs to.
3. **`core.md` gains sections for `html_to_markdown_many`, `html_to_markdown_many_with` and `version()`**,
   in the style of the existing six.
4. **`errors.md` gains a section per binding**: Rust's `Result<_, MdkaError>`, Python's raised `MdkaError`
   plus `BulkConvertResult.ok`, Node's `error` field plus promise rejection. **Check what Node actually does
   on a rejected single-file conversion before writing it** — the audit did not, and a guess here is the
   defect this slice exists to fix.
5. **The Guarantees list is split** into what holds everywhere and what is Rust-specific.

## 4. What not to do

- **Do not rewrite the usage pages.** They are per-language by design and they are correct. This is the
  *reference*, which is meant to be the one place all three appear.
- **Do not document `3.0`.** Nothing here is a preview; describe `2.9.0` exactly as it is. The differences
  become the migration guide's subject, and it must be written from an accurate *before*.
- **Do not fix the audit's other documentation findings here.** They are §6.

## 5. Criteria

1. The three false statements of §2 are gone.
2. `index.md`'s Functions table lists **every** exported function in all three bindings — 9 Rust, 10 Node,
   9 Python — with the asymmetries visible, and the Types table lists every public type.
3. `core.md` covers `html_to_markdown_many`, `html_to_markdown_many_with` and `version()`.
4. `errors.md` describes all three bindings, and the Node behaviour was **observed, not assumed** — say in
   the report how you checked.
5. **Every name in the reference is checked against the code**, by a script you paste in the report, not by
   reading. The audit's own first pass produced a false negative by matching `\bversion\b`, which occurs as
   ordinary English on nearly every page — do not repeat that shape of check.
6. `docs example gate` green; no runnable example broken; `Docs` green.
7. No change outside `docs/src/api/`.

## 6. Carried, not fixed here

Recorded so they are not lost and not silently swept in:

- **`options.md:28`** says *"Five of the eight fields below have no effect"*; **six** do — the five
  deprecated plus `unwrap_unknown_wrappers`, which the same page says has no effect at line 181. The honest
  headline is **two of eight can affect output**. *Leave it:* the sibling slice deprecates the sixth, which
  changes this sentence again. Whoever lands that one fixes it.
- **`architecture.md`'s workspace layout omits `src/table.rs`** — 637 lines, RFC 008, shipped `2.4.0`.
- **`performance-characteristics.md`** was measured at **`2.3.0` @ `c9cbbb8`**, five minors and two
  conversion milestones ago.
- **`usage-rust.md:167` and `usage-nodejs.md:188`** show `version()` → `// e.g. "2.3.0"`.
- **`usage-python.md` never mentions `version()`**, though Python exports it.

**If any of these is a one-line fix you are already touching the file for, say so in the report and ask** —
do not fold them in silently.
