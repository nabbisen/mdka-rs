# Developer Handoff — RFC 048 §7 · the `2.9.0` precondition

**RFC.** `rfcs/accepted/048-the-3.0-surface.md` — accepted by the owner, 2026-09-25
**Milestone.** `2.9.0` (minor). **`3.0` ships immediately after**, so this is the last chance to warn about anything.
**Priority.** P1 as a precondition — `3.0` cannot remove `unwrap_unknown_wrappers` until this lands.
**Prepared.** 2026-09-25
**Baseline.** `beff328` — 631 Rust (`cargo test --workspace`), 49 Node, 25 loader, 98 Python; eight workflows green
**Scope.** One deprecation, and assertions on warnings that already exist. **No conversion change, nothing removed, no signature changed.**
**Sibling slice.** `2.9.0-api-reference-handoff.md` — independent; either order.

## 1. Deprecate `unwrap_unknown_wrappers`, with a note that is true 🛑

`2.8.0` deliberately left this field undeprecated, and `src/options.rs:139–143` still explains why: the five
attribute options are inert because **Markdown has no attribute syntax** — permanent — while this one is
inert because **unwrapping currently leaves nothing observable**, which is a fact about today's renderer.

**That reasoning was right and it does not change. What changes is the decision about the `3.0` surface.**
So the note must not claim permanence:

> `since = "2.9.0"`, note: *"removed from the 3.0 surface: unwrapping leaves no Markdown-visible trace
> today, so this option cannot change the output. If wrapper handling becomes expressible it returns as a
> new option."*

**Do not reuse the attribute options' note.** *"Markdown has no attribute syntax"* is false for this field
and would be a false statement shipped in a compiler warning.

**Update `src/options.rs:139–143`'s comment in the same change.** It currently says *"Not deprecated, unlike
the fields above: it carries no `#[deprecated]` attribute and triggers no warning."* That becomes untrue the
moment you add the attribute. Keep the *distinction* it draws — it is the reason for the different note —
and change only the claim about the attribute.

**Four surfaces, as in `2.8.0`:** Rust `#[deprecated]`, Node `emitWarning`, Python `warnings.warn`, CLI
stderr (`--unwrap-wrappers`). Follow `2.8.0`'s mechanisms exactly; the CLI's shape is
`mdka: warning: …`, now asserted by `every_cli_deprecation_warning_has_the_same_shape` — **that test must
keep passing with the new warning included in it.**

**Warn only when the caller passes it**, never for a default. Same rule, same reason.

## 2. The string-form warnings: verify and assert what already exists

RFC 048 §2.2 established, against published `2.8.0`, that a mode given as a **string** behaves differently
per surface:

| Surface | today |
|---|---|
| CLI `--mode strict` | accepted, **warns** |
| Node `{mode:'strict'}` | accepted, **warns** |
| Python `mode='strict'` | **`TypeError`** — a string is not accepted at all |
| Rust `"strict".parse()` / `parse_mode` | accepted, **silent** |

**Nothing new to build.** The job is to **pin** it, because `3.0` removes these names and §6 of the RFC
depends on knowing exactly who was warned:

1. A test per surface asserting the behaviour in that table, **including Python's `TypeError`** and
   **including Rust's silence** — assert the silence deliberately, with a comment saying it is a known gap
   closed by `3.0`'s removal message, not an oversight.
2. If any surface's behaviour differs from the table, **stop and report**. The table is measured, not
   assumed, but it was measured on one host.

## 3. Not in this slice

- **Removing anything.** That is `3.0`.
- The `FromStr` removed-names table (RFC 048 §6). It belongs with the removal, because until the names are
  removed there is nothing to distinguish.
- Any conversion behaviour, any other option, either surviving mode.
- The API reference — the sibling handoff.

## 4. Criteria

1. `unwrap_unknown_wrappers` carries `#[deprecated(since = "2.9.0", …)]` with §1's note, and **the note does
   not say "Markdown has no attribute syntax"**.
2. `src/options.rs`'s comment no longer claims the field carries no attribute, and still draws the
   distinction that justifies the different note.
3. All four surfaces warn when it is passed, **each demonstrated with its actual output pasted**, and are
   silent when it is not — asserted, as in `2.8.0`.
4. `every_cli_deprecation_warning_has_the_same_shape` covers `--unwrap-wrappers` and passes.
5. §2's four assertions exist and pass, with Rust's silence asserted deliberately and commented.
6. **Output is byte-identical to `2.8.0`** in both surviving modes over the `mode_identity` corpus, with a
   positive control showing the comparison can see a difference.
7. `mode_identity.rs` P1 still passes — the field is still inert, and P1 is what proves it.
8. 631 Rust (`cargo test --workspace`) plus new cells, 49 Node, 25 loader, 98 Python; eight workflows green.

## 5. Committing and pushing

Only work that is yours and approved. Report first; a green run is not approval. Tagging, releasing and
triggering release workflows are not yours. **Name who approved anything you push.**

`git commit -F <file> -- <explicit paths>`, never `git add … && git commit`.

**One thing to know rather than act on.** `3.0` follows this release almost immediately, so this deprecation
will mostly be a *record* rather than a warning anyone lives with. The owner accepted that
(RFC 048 §12.1) and the mitigation is in `3.0`'s migration guide, not here. It is not a reason to skip the
deprecation: removing an option that was never deprecated is the thing this project does not do.

Report to `.git-exclude/review-request/048-2.9.0-precondition/README.md`, leading with §4.3 and §4.5.
